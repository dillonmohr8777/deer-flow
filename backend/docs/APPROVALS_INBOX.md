# Approvals inbox and client memory

Moved from `backend/AGENTS.md` to keep the guidance chain under its byte budget.

Agents never send outbound actions themselves: the builtin `propose_action` tool (`deerflow/tools/builtins/propose_action_tool.py`) files a `pending_actions` row (migration `0049_pending_actions`, model/repo in `persistence/approvals/`, vocabulary and payload validation in `deerflow/approvals/workflow.py`). Types: `slack_message`, `email`, `ad_change`, `other`. Rows are scoped by storage `user_id` plus the active organization (a foreign row is a 404); edit/approve/reject additionally need an active org owner/admin. Every transition is a compare-and-set `UPDATE ... WHERE status = <expected>`, so only the caller that wins `pending -> approved` runs the adapter (`app/gateway/approval_adapters.py`): exactly-once, and nothing executes before approval. Slack posts as the configured bot through the IM channel service with no footer; email, ad_change and other are stubs that leave the row `approved` with `execution_result.state == "ready_to_send"` (no live writes). Approvals and execution outcomes are audited (`approvals.approved/executed/rejected`). A crash between approve and the adapter leaves an `approved` row with no result; there is no retry endpoint yet. At enqueue, `propose_action` runs `verify_draft` on the title and payload text against the run's tool outputs: a contradicted claim refuses the proposal (message back to the agent), otherwise the report is stored on the row as `fact_check` (migration `0050_pending_action_fact_check`) and the Approvals page shows each claim as Sourced (with evidence pointer) or Unsourced. Approving a payload that was edited re-runs the check on the edited text first (the run's evidence is kept, bounded, inside `fact_check.evidence` and stripped from API responses): contradicted -> 422 and the row stays pending, unsupported -> the stored `fact_check` is refreshed so the page shows it. Client memory: an approval that was edited before approval is also written to `client_corrections` (migration `0051_client_corrections`, `persistence/approvals/corrections.py`): client key, action type, original, edited, short diff summary, time, approver. The key is `client:<id>` when a fleet binding ties the approval's `agent_name` to a client (all of that client's agents share one ledger), else `agent:<name>`; no agent means no record. `ClientCorrectionsMiddleware` adds the last 10 for the agent's client as a transient `<client_corrections>` message before the current user message (async runs only; never saved to state). Recording failures never block an approval. Tests: `tests/test_approvals_inbox.py`, `tests/test_client_memory.py`.

Client Loop filing: `POST /api/approvals/propose` (`app/gateway/routers/approvals.py`) lets the loop file the drafts it already made (client, action type, title, target, payload, source link, Gmail/Slack draft ref, thread, source evidence). It needs an internal token plus an active delegation holding `approvals:propose` (never a PAT or browser session, never granted by default); that scope cannot edit, approve or reject. It runs the shared `check_for_filing` fact check (the loop sends its sources file as evidence): contradicted -> 422, nothing filed. The row keeps `agent_name = client`, `payload.loop = {client, source_link, draft_ref}` and audits `approvals.proposed`. Tests: `tests/test_approvals_loop_filing.py`.

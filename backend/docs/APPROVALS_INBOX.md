# Approvals inbox and client memory

Moved from `backend/AGENTS.md` to keep the guidance chain under its byte budget.

Agents never send outbound actions themselves: the builtin `propose_action` tool (`deerflow/tools/builtins/propose_action_tool.py`) files a `pending_actions` row (migration `0049_pending_actions`, model/repo in `persistence/approvals/`, vocabulary and payload validation in `deerflow/approvals/workflow.py`). Types: `slack_message`, `email`, `ad_change`, `other`; extensions add more via `register_action_type` and `register_adapter` (see `extensions/report-studio/README.md` for `deploy_report`). Rows are scoped by storage `user_id` plus the active organization (a foreign row is a 404); edit/approve/reject additionally need an active org owner/admin. Every transition is a compare-and-set `UPDATE ... WHERE status = <expected>`, so only the caller that wins `pending -> approved` runs the adapter (`app/gateway/approval_adapters.py`): exactly-once, and nothing executes before approval. Slack posts as the configured bot through the IM channel service with no footer; email, ad_change and other are stubs that leave the row `approved` with `execution_result.state == "ready_to_send"` (no live writes). Approvals and execution outcomes are audited (`approvals.approved/executed/rejected`). A crash between approve and the adapter leaves an `approved` row with no result; there is no retry endpoint yet. At enqueue, `propose_action` runs `verify_draft` on the title and payload text against the run's tool outputs: a contradicted claim refuses the proposal (message back to the agent), otherwise the report is stored on the row as `fact_check` (migration `0050_pending_action_fact_check`) and the Approvals page shows each claim as Sourced (with evidence pointer) or Unsourced. Approving a payload that was edited re-runs the check on the edited text first (the run's evidence is kept, bounded, inside `fact_check.evidence` and stripped from API responses): contradicted -> 422 and the row stays pending, unsupported -> the stored `fact_check` is refreshed so the page shows it. Client memory: an approval that was edited before approval is also written to `client_corrections` (migration `0051_client_corrections`, `persistence/approvals/corrections.py`): client key, action type, original, edited, short diff summary, time, approver. The key is `client:<id>` when a fleet binding ties the approval's `agent_name` to a client (all of that client's agents share one ledger), else `agent:<name>`; no agent means no record. `ClientCorrectionsMiddleware` adds the last 10 for the agent's client as a transient `<client_corrections>` message before the current user message (async runs only; never saved to state). Recording failures never block an approval. Tests: `tests/test_approvals_inbox.py`, `tests/test_client_memory.py`.

Slack DM: with `channels.slack.approvals_dm.enabled`, each new pending row is DM'd to `user_ids` with Approve / Edit / Skip buttons (`app/channels/slack_approvals.py`; details in `app/channels/AGENTS.md`). Skip maps to reject; Approve uses the same adapters, so email still only becomes `ready_to_send`.

Composio: two mandatory built-in MCP guards surround auth/custom interceptors: an outer preflight withholds writes before any downstream interceptor, and a final boundary rechecks custom rewrites/retries immediately before transport. The outer boundary binds the actual server, authenticated actor/organization and runtime correlation identity in an immutable task-local origin; relabeling the server or replacing/mutating the runtime cannot escape the final boundary. Every `composio-*` server is covered, including `composio-sean` and future `composio-me`; there is no user exemption or request-controlled bypass. Only the explicit manage-connections/search-tools/get-schemas controls and the exact read catalog below pass. Unknown meta tools, remote code/bash/proxy execution, unsupported shapes, or any write in a multi-execute batch withhold the whole exact call. Provider behavior tags and a read-shaped name do not grant execution authority.

Account read policy: nine code-owned exact actions with required fields, allowed argument names/types and string-only arrays. [Gmail](https://docs.composio.dev/toolkits/gmail), version `20261018_00`: `GMAIL_FETCH_EMAILS`, `GMAIL_FETCH_MESSAGE_BY_MESSAGE_ID`, `GMAIL_LIST_LABELS`, `GMAIL_GET_PROFILE`. [HubSpot](https://docs.composio.dev/toolkits/hubspot), version `20261020_01`: `HUBSPOT_READ_CONTACT`, `HUBSPOT_LIST_CONTACTS`. [Slack](https://docs.composio.dev/toolkits/slack), version `20261020_00`: `SLACK_SEARCH_ALL`, `SLACK_SEARCH_MESSAGES`, `SLACK_FETCH_CONVERSATION_HISTORY`.

Existing public research also remains automatic through ten exact entries, directly or inside multi-execute: [Composio Search](https://docs.composio.dev/toolkits/composio_search), version `20260903_00`: `COMPOSIO_SEARCH_WEB`, `COMPOSIO_SEARCH_NEWS`, `COMPOSIO_SEARCH_TRENDS`, `COMPOSIO_SEARCH_GOOGLE_MAPS`, `COMPOSIO_SEARCH_EXA_SIMILARLINK`, `COMPOSIO_SEARCH_NPPESNPI_LOOKUP`. [Inspo MCP](https://docs.composio.dev/toolkits/inspo_mcp), version `20260925_00`: `INSPO_MCP_SEARCH_SCREENS`, `INSPO_MCP_GET_SCREEN`. [GoDaddy MCP](https://docs.composio.dev/toolkits/godaddy_mcp), version `20261018_00`: `GODADDY_MCP_DOMAINS_CHECK_AVAILABILITY`, `GODADDY_MCP_DOMAINS_SUGGEST`. These use the same required-field and allowed-key/type checks; for example, GoDaddy availability requires `domains` as a string, Inspo screen retrieval requires `slug`, and Maps requires `q`. There is no server exemption.

All nineteen actions' public documented input parameters were inspected on 2026-10-23; no provider/schema API probe is required at execution. Unknown actions or argument shapes require approval, including generic query/compound actions and extra unreviewed arguments on a known research action. This is a reviewed subset, not complete toolkit/workflow coverage. Further read entries need source review of their exact operation and input contract; unfamiliar legitimate reads can still be explicitly approved.

Composio proposals use the existing `composio_tool_call` validator/adapter registry. Their `user_id` is the authenticated proposer and `organization_id` is the active organization, including shared workspaces. Active staff proposers may approve or decline their own pending proposal. Approving another actor's proposal requires the active workspace owner (`organization_members.role == "owner"`); an admin who is not the owner receives 403 before any decision or execution claim. Owners/admins retain list/read/reject oversight, and admins can still approve their own proposals. Ordinary members cannot decide another member's proposal, and deployment-level admin status alone grants no organization authority. Current-org contacts and contacts of the current exact bound customer are excluded; unrelated assignments elsewhere preserve staff access. Other organizations remain hidden. The inbox still merges own rows with owner/admin Composio oversight rows, deduplicates, sorts newest first and applies the existing status filter and limit. Non-Composio decision and edit rules are unchanged. Every Composio decision audits the actual decider, proposer, organization and action id; repeated decisions return 409.

Approval requires a current operator-granted HTTP/SSE `user_auth` binding for the active staff proposer. Public, missing, OAuth-only, request-credential and future dynamic-session bindings fail closed before the decision. This checks the configured grant, not the provider's actual OAuth account identity; native owner validation remains required. An in-process authority binds one immutable action to the actual deciding actor, proposer, organization and transient connection. The signed-in user remains the deciding actor throughout. Dedicated repository methods recheck current staff status, membership and storage scope; the adapter reloads the action, and the final MCP guard rechecks those facts and the exact proposer credential headers after custom interceptors. The authority cannot authorize another action or survive its scoped context. Private MCP/Brain policies remain unchanged. Coverage: `tests/test_composio_approval_handoff.py` and `tests/test_composio_admin_oversight.py`, using real UUID users, production auth middleware, SQLite and fake MCP transport.

A SHA-256 primary key over actor, active org, thread, run, logical server and runtime tool-call ID deduplicates retries durably without a migration. Reuse with conflicting exact tool/arguments is refused; these approval payloads are immutable. Rows retain the logical server, exact tool name/arguments and correlation ID, never transport URLs/headers/keys. Normalized credential carrier keys, nested carriers, URL userinfo and auth-bearing query/fragment parameters are rejected before a row or identity hash is created, returning `not_executed / credential_bearing_arguments`. Values are never echoed, redacted and executed, or substituted into another payload. Ordinary non-auth URLs remain exact. This deterministic screening covers recognized credential carriers; arbitrary free text is not a secret vault and must never be supplied with credentials.

After the pending-to-approved CAS, the Composio adapter reloads current scoped MCP configuration and atomically claims an approved row whose execution result is unset. Before calling upstream it commits `execution_result.state = outcome_unknown`. Only that winner receives the existing one-use capability bound to the proposer, organization and exact call, together with the scoped deciding authority; the final guard consumes it before the upstream attempt. No model argument or runtime flag creates either capability. Repeated/concurrent decisions or adapter calls cannot release another attempt. A timeout, cancellation, lost response, or process crash after the claim leaves the row approved/unknown and fenced against automatic replay; reconcile the destination before any deliberately new proposal. This is at most one upstream attempt per action, not a transactional exactly-once guarantee for external effects. A returned MCP result alone does not establish the intended business outcome. Offline coverage: `tests/test_composio_approval_guard.py`.

Client Loop filing: `POST /api/approvals/propose` (`app/gateway/routers/approvals.py`) lets the loop file the drafts it already made (client, action type, title, target, payload, source link, Gmail/Slack draft ref, thread, source evidence). It needs an internal token plus an active delegation holding `approvals:propose` (never a PAT or browser session, never granted by default); that scope cannot edit, approve or reject. It runs the shared `check_for_filing` fact check (the loop sends its sources file as evidence): contradicted -> 422, nothing filed. The row keeps `agent_name = client`, `payload.loop = {client, source_link, draft_ref}` and audits `approvals.proposed`. Tests: `tests/test_approvals_loop_filing.py`.

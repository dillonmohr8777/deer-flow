# Identity-bound tools: surface inventory

lane/identity-bound-tools, built on `fork/integrate/m1-20260922`. IDEA: every
agent-visible tool and every Gateway route that accepts a caller-supplied
identifier must reject a cross-user or cross-organization request the same
way it rejects a missing one: no data, no write, no existence oracle. M3
(`plans/momentum-m3-isolation-plan.md`) built the organization-isolation
mechanism (`resolve_organization_id`, `organization_for_write`, delegations
for internal callers) and already ships thorough proof at the Gateway-route
and repository layer: `backend/tests/test_org_isolation_a_projects.py`
through `..._g_memory.py`, plus `test_org_isolation_phase2.py` (2673 lines,
about 50 test functions, using the shared `org_isolation_fixtures.py` world:
orgs A, B, C are private organizations owned by users a, b, c; org S is a
shared workspace owned by a with c as an active admin and b as an outsider).

This lane's job is narrower: prove the same claim holds one layer further
in, at the agent-callable **tool** function the model actually invokes mid
run, for every tool whose arguments include an identifier the model supplies
(not the Gateway/runtime). Section A inventories the Gateway-route surface
and cites the existing proof (no new tests needed there; it is thorough).
Section B inventories every agent-visible tool and marks which id parameters
are genuinely model-suppliable versus resolved from server-owned run
context. New tests: `backend/tests/test_identity_bound_tools.py`.

Every "proven" row below either cites a passing test or was run as part of
this lane's own new test file. Rows I could not prove are listed under Gaps
at the end, with the reason.

## Gaps

- **`SubagentBatchRepository._set_control`** (`pause_batch`/`resume_batch`/`cancel_batch` in `packages/harness/deerflow/persistence/subagent_batches/sql.py`) checks `batch.user_id` but, unlike `get_batch`/`list_by_thread`, does not also call `_batch_organization_visible`. Read the code: that helper is explicitly "defense in depth beside the user_id check," guarding a NULL-organization (pre-M3-migration, quarantined) row from matching by `user_id` coincidence, not the live two-different-users case this lane's fixtures build. My two-user/two-org and shared-workspace tests (real, freshly stamped rows) cannot reproduce a NULL-organization row, so they do not exercise this asymmetry and it is not a proven leak under this lane's own test standard. It also sits in a file outside this lane's edit authorization (not `services.py`/`auth_middleware.py`/`internal_auth.py`/`authz.py`/`persistence/organizations/*`). Flagging it for the M3 core-file owners; it is the same class of work already tracked as gap 1 in `plans/momentum-m3-isolation-plan.md` ("organization_id == active org beside every user filter, 13 tables").
- **Managed subagent catalog GET readable by non-admins with prompts redacted** (`backend/AGENTS.md` note via the M3 plan, section 7): plan section 7 already flags this as "confirm that is intended," not a defect. I did not independently re-litigate intent; carried forward unresolved.
- **Path traversal inside a thread's own sandbox/outputs directory** (`present_file_tool`, `view_image_tool`, sandbox `read`/`write`/`str_replace`): explicitly out of scope. This lane's IDEA is cross-user/cross-organization identifier binding; a caller reading outside its own already-authorized thread directory is a different control (existing `test_sandbox_tools_security.py`, `test_sandbox_authorization.py` own that surface).
- **Skill catalog visibility filtering** (`app/gateway/authz.py`, commit `d811143b`, PR #5489): real and recent, but skills are not one of the task's enumerated resource types (thread/run/document/project/upload/artifact/memory item/scheduled task/MCP task/subagent task/channel/invitation) and already has dedicated coverage outside the M3 lane files; noted, not re-tested here to keep this lane's scope to its brief.
